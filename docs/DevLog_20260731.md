# Day 5 — Power Chain Analysis & U-Boot Network Fix (2026-07-31)

**Objective:** Understand the board's discrete power architecture, then fix the
U-Boot ethernet failure (`Could not get PHY` / `address not set`) end-to-end:
custom DTS, crash recovery via UUU, schematic-based debugging, and a final
MAC-address fix that brings `eth1 [PRIME]` to life.

---

## 1. Power Chain Analysis

The ATK-IMX6U core board uses a **discrete (non-PMIC) power solution** — every
rail is generated by standalone regulators, not an I2C-controlled PMIC.

```
[DC5V input]
   ├── U7 (ME6209A33M3G LDO) ──► VDD_SNVS_3V3 ──► SoC SNVS domain (RTC / low-power)
   │                                    │
   │                        SoC asserts PMIC_ON_REQ in hardware
   │                                    ▼
   ├── U8 (TMI3113 DCDC) ◄── EN pin  ──► DCDC_3V3 (main 3.3V)
   │                                    │
   │                        DCDC_3V3_PG (Power Good)
   │                                    ▼
   ├── U6 (MT3420B) ──► SOC_IN (1.2V, ARM core)
   ├── U11 (MT3420B) ──► DRAM_1V35 (1.35V, DDR3L)
   ├── U9 (TMI6050) ──► VCC_SD (3.3V)
   └── U12 (XC6206P282MR) ──► NVCC_CSI (2.8V)
```

Key conclusions:

- `PMIC_ON_REQ` is pulled high by a **pure hardware state machine** in the SNVS
  domain — no CPU code involved (solves the "chicken-and-egg" power question).
- None of the regulators expose an **I2C interface**; voltages are fixed by
  resistor dividers. → U-Boot neither needs nor can control the PMIC, so
  `CONFIG_DM_PMIC` stays disabled.
- Reset is generated by **MAX809R** (reset supervisor), releasing `POR_B` about
  ~140 ms after 3.3V is stable.
- Software power-off: the CPU writes `SNVS_LPCR` to deassert `PMIC_ON_REQ`.

The MT3420B is a pure analog buck (SOT23-6, no register interface); it is only
enabled by its EN pin (hardwired to `DCDC_3V3_PG`), `VOUT = 0.6V×(1+R1/R2)`.

## 2. U-Boot DDR3L Build & boot0 Flashing

Since the PMIC is independent, flashing a U-Boot built with the custom DDR3L DCD
is safe. Build procedure (Buildroot toolchain, GCC 12.3.0):

| Step | Action | Result |
|:---:|--------|:---:|
| 1 | Backup stock `imximage.cfg` → `imximage.cfg.orig` | ✅ |
| 2 | Apply Nanya NT5CC256M16EP-EK DDR3L cfg | ✅ |
| 3 | `make mx6ull_14x14_evk_defconfig` | ✅ |
| 4 | `make CROSS_COMPILE=arm-buildroot-linux-gnueabihf- -j4` | ✅ `MKIMAGE u-boot-dtb.imx` |
| 5 | Verify DCD (5 MRS commands: MR2/MR3/MR1/MR0 + ZQ cal) | ✅ |

Flashing to eMMC boot0 (via SSH, board running Linux):

```bash
echo 0 > /sys/block/mmcblk1boot0/force_ro
dd if=u-boot-dtb.imx of=/dev/mmcblk1boot0 bs=1K seek=1 conv=fsync
echo 1 > /sys/block/mmcblk1boot0/force_ro
# read back and compare (1 KB offset, 617472 bytes)
```

The boot0 layout keeps the IVT at offset 0x400 (= `u-boot-dtb.imx` offset 0),
with the first 1 KB of boot0 unused (all zeros).

## 3. DTB Loading Fix (Phase 1 & 2)

After flashing, Linux failed to boot with the correct device tree.

- **Phase 1 (verify):** at the U-Boot prompt, `setenv fdt_file imx6ull-atk.dtb`
  + `saveenv` → Linux boots correctly (UART3 / dual FEC / SPI all fine).
- **Phase 2 (permanent):** edit `include/configs/mx6ullevk.h` line 89
  (backup `.orig` first):

```c
"fdt_file=undefined\0"  →  "fdt_file=imx6ull-atk.dtb\0"
```

The NXP `findfdt` logic only overrides `fdt_file` when it is `undefined`, so
the board now always loads our DTB even after the environment is wiped.

## 4. Custom U-Boot DTS & Crash (Phase 3 / Phase 4)

- **Phase 3:** copied `DTS/imx6ull-atk.dts` into
  `uboot-imx/arch/arm/dts/imx6ull-atk.dts`, added
  `#include "imx6ul-14x14-evk-u-boot.dtsi"`, registered it in the DTS
  Makefile, and set `CONFIG_DEFAULT_DEVICE_TREE="imx6ull-atk"` in the
  defconfig.
- **Phase 4:** restoring `phy-supply` triggered an **infinite reboot crash**
  (`undefined instruction` after `Get shared mii bus on ethernet@2188000`) —
  a U-Boot bug in handling the shared MDIO bus (both `ethphy0`/`ethphy1` are
  declared under fec2's `mdio` node, while fec1 also references `ethphy1`).

## 5. UUU Emergency Recovery

The board was bricked by the crash — recovered via Serial Downloader mode:

```
uuu_version 1.2.39
SDP: boot -f _flash.bin          # our own normal U-Boot (DDR3L DCD)
FB: ucmd mmc dev 1 1             # select eMMC boot0 hardware partition
FB: download -f boot0.bin
FB: ucmd mmc write 0x83800000 0x0 0x2000   # 4 MB = 0x2000 blocks
FB: ucmd mmc dev 1 0
FB: done
```

Key gotchas learned:

- UUU script must start with `uuu_version 1.2.39` and run from a directory
  containing `uuu.auto`.
- The MFG SPL (`u-boot-with-spl.imx`) fails with `Unsupported Boot Device`;
  use **our own** U-Boot image instead.
- `FB: flash bootloader` fails without
  `CONFIG_FASTBOOT_MMC_BOOT_SUPPORT`; use native U-Boot commands
  (`mmc dev 1 1` + `mmc write`) instead.

---

## 6. Plan E: Disable fec1 in U-Boot DTS

Root cause of the crash: shared MDIO bus between fec1 and fec2 (U-Boot bug).
Workaround in the U-Boot `imx6ull-atk.dts`:

```c
&fec1 { status = "disabled"; };
```

After this: crash gone, and the boot log reduced to
`Could not get PHY for FEC1: addr 1` (fec2's MDIO bus name is `FEC1` because
its device sequence is 1).

---

## 7. Schematic Investigation (decisive)

Extracted both schematics with `pdftotext`:

1. **PHYs are on the baseboard** (U14/U15 = SR8201F), not the core board.
2. **PHY reset pins have a 10K pull-up** to 3.3V → a PHY is not held in reset
   by default (explains why misconfigured reset still "worked" in Linux).
3. **Baseboard J2 is authoritative:**
   `J2_9 = SNVS_TAMPER8 (GPIO5_IO08) = ENET2_RST`, `J2_10 = SNVS_TAMPER7
   (GPIO5_IO07) = ENET1_RST`.
4. NXP dtsi address mapping: `fec1 = ethernet@2188000 = ENET2`,
   `fec2 = ethernet@20b4000 = ENET1`.

---

## 8. Cross-wired phy-reset-gpios Fix

Comparing all three `imx6ull-atk.dts` copies (GitHubUpload / linux-imx /
uboot-imx) against the schematic showed the reset GPIOs were **swapped**:

| Node | Wrong (original) | Correct (J2) |
|------|:---:|:---:|
| fec1 (ENET2) | `<&gpio5 7>` ❌ | **`<&gpio5 8>`** (ENET2_RST=TAMPER8) |
| fec2 (ENET1) | `<&gpio5 8>` ❌ | **`<&gpio5 7>`** (ENET1_RST=TAMPER7) |

The pinctrl groups were already correct — only the GPIO numbers were swapped.
All three files were fixed in sync and the Linux DTB redeployed (36512 bytes).

## 9. Final Network Fix

### 9.1 PHY ID confirmed: `0x001CC816`

Manual MDIO reads from the U-Boot prompt (write `MII_DATA` command, read back)
returned:

| Register | Value | Datasheet (SR8201F_VB, Table 13/14) |
|----------|:-----:|:---:|
| reg0 (BMCR) | `0x3100` | standard BMCR (100M + AN) |
| reg1 (BMSR) | `0x7869` | standard BMSR |
| reg2 (PHYID1) | `0x001C` | OUI[21:6] = `001Ch` ✅ |
| reg3 (PHYID2) | `0xC816` | OUI_LSB(110010) + Model(000001) + Rev(0110) ✅ |

> **SR8201F PHY ID = `0x001C_C816`** — exactly as the datasheet says.
> (Interesting: Linux reports `0x00110140`, which does NOT match the datasheet,
> but does not affect functionality since the generic PHY driver is used.)

### 9.2 Real blocker: MAC address

With the PHY now responding, the only remaining error was:

```
Error: ethernet@20b4000 address not set.
```

`net/eth-uclass.c` rejects the device when neither the environment (`ethaddr`)
nor the driver-provided MAC is valid. The OTP fuses are unblown (Linux used
random MACs). Fix:

```kconfig
CONFIG_NET_RANDOM_ETHADDR=y    # in configs/mx6ull_14x14_evk_defconfig
```

The debug `MDIO_DBG` printf in `fec_mdio_read()` was also removed.

### 9.3 Result

```
Net:
Warning: ethernet@20b4000 (eth1) using random MAC address - b2:82:77:4e:9a:cb
eth1: ethernet@20b4000 [PRIME]

=> ping 192.168.1.1
Using ethernet@20b4000 device
host 192.168.1.1 is alive
```

Fixed MAC persisted:

```text
setenv eth1addr 00:1c:c8:00:00:01
setenv ipaddr 192.168.1.100
saveenv
```

After boot, Linux `eth0` shows `00:1C:C8:00:00:01` (U-Boot patches the DTB
with the environment MAC). Build artifact: `u-boot-dtb.imx` (629,760 B,
MD5 `32661e6f...`, timestamp `Jul 31 2026 - 11:44:31`).

| Issue | Status | Resolution |
|-------|:------:|------------|
| U-Boot with `phy-supply` crashes (infinite reboot) | ✅ Fixed | Plan E: disable fec1 in U-Boot DTS (shared MDIO bus bug) |
| Board bricked | ✅ Recovered | UUU Serial Downloader with our own U-Boot + `mmc write` to boot0 |
| `Could not get PHY for FEC1: addr 1` | ✅ Fixed | phy-reset-gpios were cross-wired; corrected per schematic J2 |
| MDIO reads looked "garbled" (0x9000 / 0x001C ...) | ✅ Explained | Values match the SR8201F datasheet; reg0=0x9000 was the PHY still in reset |
| `address not set` | ✅ Fixed | `CONFIG_NET_RANDOM_ETHADDR=y` + fixed `eth1addr` in env |
| Misleading experiments (ANATOP bit21, ECNTRL, PAD 0x0334) | ✅ Ruled out | Register snapshot comparison (Linux vs U-Boot) showed no relevant difference |

## Key Takeaways

1. **U-Boot and Linux have fully independent DTS ecosystems** — same base dtsi,
   different top-level DTS files; changes must be made in both.
2. **Discrete-power boards need no U-Boot PMIC control** — `CONFIG_DM_PMIC`
   stays off; DCD changes only affect DDR init.
3. **`address not set` is a MAC problem, not a PHY problem** —
   `CONFIG_NET_RANDOM_ETHADDR=y` is the one-liner fix.
4. **SR8201F PHY ID = `0x001CC816`** — the datasheet is authoritative.
5. **eMMC boot0 layout**: first 1 KB unused, IVT at 0x400 (offset 0 of
   `u-boot-dtb.imx`) — flash with `dd bs=1K seek=1` or a 4 MB UUU image.
6. **Always back up boot0** before flashing; the UUU recovery flow is the
   lifeline when a bad U-Boot bricks the board.
